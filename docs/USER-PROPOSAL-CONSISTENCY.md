# 提案映射与数据库迁移说明（先看这份）

这份文档只回答两个问题：提案通过后，新院系和新课程分类能不能正常使用；上线前为什么要运行迁移工具。

## 先说结论

可以。提案通过时，新院系和新课程分类会先写入 MongoDB，再刷新到 Redis，重启后也能从 MongoDB 重新加载，因此不会因为重启丢失。

校区是例外：提案只能使用已经存在的校区，不能通过提案创建全新校区。未知校区会在创建、修改或审批提案时被拒绝。

| 数据 | 提案能否创建新值 | 持久化位置 | Redis 用途 |
| --- | --- | --- | --- |
| 校区 | 不能，只能选择已有校区 | MongoDB `mapping` | 加速名称和编号互查 |
| 院系 | 可以，在审批通过时创建 | MongoDB `mapping` | 加速名称和编号互查 |
| 课程分类 | 可以，在审批通过时创建 | MongoDB `mapping` | 加速名称和编号互查 |

## 当前实际运行逻辑

### 查询映射

查询校区、院系和课程分类时：

1. 先查 Redis Hash；
2. Redis 没有时查 MongoDB；
3. MongoDB 查到后，把结果回填到 Redis；
4. 批量把课程编号组装为名称时使用 `HMGET`，一次查询多个编号，不会为每个字段单独请求 Redis。

Redis 同时保存两个方向：

- `name -> code`：把名称转换为编号；
- `code -> name`：把编号转换为名称。

MongoDB 是唯一真源。即使 Redis 被清空，映射也不会丢失。

### 通过提案

管理员通过提案时，后端按下面的顺序工作：

```text
校验校区必须已存在
        ↓
MongoDB 事务中创建缺少的院系/课程分类
        ↓
MongoDB 事务中写课程、教师、提案状态、贡献值和审计日志
        ↓
事务提交成功
        ↓
从 MongoDB 刷新 Redis 映射
```

如果 MongoDB 事务中的任何一步失败，整笔操作会回滚，不会出现“提案显示已通过，但院系或课程没有写入”的半成品。

如果 MongoDB 已提交、但随后 Redis 刷新暂时失败，数据仍然安全地保存在 MongoDB。后续缓存未命中或服务重启时，会重新写入 Redis。

### 服务重启

服务启动时会从 MongoDB 读取全部映射，先写入 Redis 临时键，六个 Hash 全部准备完成后再一次性切换为正式键。其他服务实例看到的只会是完整旧版本或完整新版本，不会读到一半数据。

## 迁移工具到底是做什么的

迁移工具 `cmd/migrate-v2` 是一次性的生产数据库升级工具，不是接口运行时的一部分，也不是把测试 JSON 导入线上。

旧版本主要把校区、院系、课程分类写在后端代码的静态映射表中。新版本改为 MongoDB 持久化、Redis 加速，所以升级时需要把数据库准备成新结构。

它不代表旧数据库的所有字段都有问题，也不只是添加索引。主要工作如下：

| 迁移工作 | 为什么需要 |
| --- | --- |
| 建立完整的 `mapping` 数据 | 让原来只存在代码里的映射真正保存到 MongoDB |
| 建立 `mapping_counter` | 新增院系或分类时安全分配新编号，避免多个实例分配出重复编号 |
| 检查静态编号与线上动态编号冲突 | 线上已经新增的数据不能被旧静态编号覆盖；有冲突就停止并报告 |
| 创建唯一索引 | 防止相同类型出现重复名称或重复编号 |
| 检查并修复能明确判断的历史脏数据 | 例如课程映射编号为 `0`、重复 `proposalId`、昵称大小写冲突等；无法确定时停止，不猜测、不覆盖 |

所以，迁移同时包含“数据落库、冲突检查、少量历史数据修复和索引创建”。某个线上数据库是否真的存在历史脏数据，只有执行试运行后才能知道。

## `dry-run` 是什么意思

`dry-run` 就是试运行：读取线上数据库并生成迁移计划和冲突报告，但不修改数据库。

- 没有冲突：审核计划后，才允许执行正式迁移；
- 有冲突：工具停止，报告具体冲突，不能擅自覆盖线上数据；
- 处理冲突后：必须重新执行 `dry-run`，得到新的无冲突计划。

这样做是因为当前提供的旧 JSON 不包含线上后来新增的全部数据，不能拿它直接覆盖生产数据库。

## 哪些环境需要迁移

- 从旧后端升级的线上数据库：必须先备份，再 `dry-run`，无冲突后正式迁移；
- 全新的空数据库：部署前需要初始化映射和计数器；
- 已经成功迁移到 v2 的数据库：不要盲目重复正式迁移，只做检查和上线验证。

完整命令、备份、冲突处理和回滚步骤见 [MIGRATION-V2.md](./MIGRATION-V2.md)。那份是给实际执行上线的运维手册，本文件才是日常理解逻辑时首先阅读的说明。

## 上线后最小验证

1. 创建一个使用已有校区、全新院系和全新课程分类的提案；
2. 管理员通过提案；
3. 查询课程，确认院系和课程分类名称正确；
4. 清空本应用使用的 Redis 逻辑库或重启后端；
5. 再次查询课程，仍应得到相同名称；
6. 在 MongoDB `mapping` 集合中确认新院系和新分类仍然存在；
7. 使用未知校区创建或审批提案，接口应拒绝请求。

这组验证通过，就证明新增映射已经持久化到 MongoDB，Redis 只承担可重建的查询加速作用。
