# 提案映射与数据库迁移说明（先看这份）

这份文档只回答两个问题：提案通过后，新院系和新课程分类能不能正常使用；上线前为什么要运行迁移工具。

## 先说结论

可以。提案通过时，新院系和新课程分类会先写入 MongoDB，再刷新到 Redis，重启后也能从 MongoDB 重新加载，因此不会因为重启丢失。

校区是例外：提案只能使用已经存在的校区，不能通过提案创建全新校区。未知校区会在创建、修改或审批提案时被拒绝。

| 数据 | 提案能否创建新值 | 持久化位置 | Redis 用途 |
| --- | --- | --- | --- |
| 校区 | 不能，只能选择已有校区 | MongoDB `mapping` | 加速名称和编号互查 |
| 院系 | 可以，在审批通过时创建 | MongoDB `mapping` | 加速名称和编号互查 |
| 课程分类 | 可以，在审批通过时创建 | MongoDB `mapping` | 加速名称和编号互查 |

## 当前实际运行逻辑

### 查询映射

查询校区、院系和课程分类时：

1. 先查 Redis Hash；
2. Redis 没有时查 MongoDB；
3. MongoDB 查到后，把结果回填到 Redis；
4. 批量把课程编号组装为名称时使用 `HMGET`，一次查询多个编号，不会为每个字段单独请求 Redis。

Redis 同时保存两个方向：

- `name -> code`：把名称转换为编号；
- `code -> name`：把编号转换为名称。

MongoDB 是唯一真源。即使 Redis 被清空，映射也不会丢失。

### 通过提案

管理员通过提案时，后端按下面的顺序工作：

```text
校验校区必须已存在
        ↓
MongoDB 事务中创建缺少的院系/课程分类
        ↓
MongoDB 事务中写课程、教师、提案状态、贡献值和审计日志
        ↓
事务提交成功
        ↓
从 MongoDB 刷新 Redis 映射
```

如果 MongoDB 事务中的任何一步失败，整笔操作会回滚，不会出现“提案显示已通过，但院系或课程没有写入”的半成品。

如果 MongoDB 已提交、但随后 Redis 刷新暂时失败，数据仍然安全地保存在 MongoDB。后续缓存未命中或服务重启时，会重新写入 Redis。

### 服务重启

服务启动时会从 MongoDB 读取全部映射，先写入 Redis 临时键，六个 Hash 全部准备完成后再一次性切换为正式键。其他服务实例看到的只会是完整旧版本或完整新版本，不会读到一半数据。

## 数据准备

旧版迁移已完成，一次性迁移工具和课程类别、院系的静态列表已从当前代码移除，需要追溯旧迁移流程时请查阅 Git 历史。

现有环境直接使用 MongoDB 中的映射。全新环境需要准备与业务记录编号一致的映射数据，尤其是必须预先存在的校区；应用启动不会再用旧课程类别、院系列表填充数据库。

## 上线后最小验证

1. 创建一个使用已有校区、全新院系和全新课程分类的提案；
2. 管理员通过提案；
3. 查询课程，确认院系和课程分类名称正确；
4. 清空本应用使用的 Redis 逻辑库或重启后端；
5. 再次查询课程，仍应得到相同名称；
6. 在 MongoDB `mapping` 集合中确认新院系和新分类仍然存在；
7. 使用未知校区创建或审批提案，接口应拒绝请求。

这组验证通过，就证明新增映射已经持久化到 MongoDB，Redis 只承担可重建的查询加速作用。
