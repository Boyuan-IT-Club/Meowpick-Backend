# 课程与教师资料提案设计

本文描述本分支已实现的接口和业务规则。原需求文档只定义新增课程提案；本设计新增修改课程与修改教师，并保留统一的提交、审核、点赞、额度、个人历史和操作日志流程。实现差异记录在本地 `IMPLEMENTATION-NOTES.local.md`。

## 业务边界

- `type` 使用 `create_course`、`update_course`、`update_teacher`。历史缺失 `type` 的提案读取为 `create_course`。`status` 仍独立表示 `pending`、`approved`、`rejected`。
- 每份修改提案只针对一个已存在的课程 ID 或教师 ID。课程提案可修改名称、代码、分类、开课院系、校区和完整任课教师列表；教师提案可修改姓名、职称、所属院系。课程更换任课教师不改已有教师资料。
- 课程提案的任课教师列表可引用已有教师 ID，也可附带新教师。新教师在审批通过时才创建。拟创建教师有同名候选时，管理员选择复用还是创建；不按姓名自动合并。
- 同名同代码但教师姓名完全不重合的课程可独立存在。新增课程提案只要课程名相同，就列入管理员的疑似列表；管理员也可按课程名模糊搜索待审提案并手动选择共同审批成员。同名仅提示，不自动认定同课。
- 新方案移除 `title`，显示名按提案类型和目标资料生成。旧数据的 `title` 保留在数据库作历史兼容，不作为新提案输入或对外显示字段。`content` 继续是补充说明。
- 独立的管理员新增教师接口 `POST /api/teacher/add` 在新方案中移除；新教师随课程提案进入审核。现有已弃用的 `GET /api/teacher/suggest` 单独清理，不与本变更混淆。

## 提交与变更表达

- `create_course` 提交完整课程资料；`update_course`、`update_teacher` 提交目标 ID 与 `suggested` 对象，里面**只放用户想修改的字段及建议值**。例如 `{"type":"update_course","targetId":"课程ID","suggested":{"code":"CS102"}}` 表示只建议把代码改成 `CS102`，其他字段保持当前值。后端在创建提案时读取并保存该字段的原值；客户端不能指定可信原值。
- `suggested` 中缺席表示不修改；教师职称、所属院系显式传空字符串表示申请清空。教师姓名及课程名称、代码、分类、开课院系不得清空；课程校区至少一项。任课教师列表作为一个字段提交完整新列表。
- 创建或更新待审提案时规范化文本首尾空白；自动归组不使用模糊匹配。新增课程须课程名、代码、完整教师身份集合、校区集合、分类、开课院系六项都相同；修改课程／教师按目标 ID 与拟改字段和值判断。教师与校区列表均按集合比较，顺序无关。
- 同一作者对同一个自动组不重复建待审提案。不同作者可提交相同内容，也可对同一目标提出不同建议。已生效后提交的无实际变更建议直接返回专用业务错误码。
- 被拒绝的提案重新提交生成新提案。管理员编辑待审提案保存的是共同最终草稿 `finalCourse`／`final`，同步至原始自动组及后续加入的相同提案；各作者的 `course`／`suggested`／`before`／`content` 保持不变，积分以原建议计算。

## 审批、重复与冲突

- 新增课程的**待审提案重复**与**已生效课程重复**分别处理。不同作者提交的待审新增课程提案允许并存。课程名、代码、完整任课教师身份集合（无序）、校区集合（无序）、分类、开课院系六项规范化后都相同的待审提案自动成组：已有教师必须是相同 ID，新教师必须是相同姓名；已有教师与新教师即使同名、不同 ID 的已有教师即使同名，都不自动归组。新教师即使存在现实中的同名不同人风险，仍按同名自动归组；教师职称、`content` 和匿名设置不参与自动组判断。审批其中一份，整组采用管理员的一份最终课程资料共同通过，课程只创建一次，每位作者按自己的原建议计分。课程名相同但其余条件有差异的提案只作为疑似项；管理员按字段差异判断是否另行勾选加入本次共同审批。教师名单只部分重合不自动归并。
- 对已生效课程，提交修改提案但没有实际变更时应直接返回稳定业务错误码。新增课程审批时如果管理员发现正式课程已经存在，由管理员手动拒绝所选新增提案并附已有课程信息，引导用户另提修改；管理员可勾选多份提案并一次填写共同拒绝理由。发现正式课程不会自动拒绝整组，也不得“跳过创建却标记通过并结算贡献值”。已有课程与待审提案候选分组展示，不能混为一类。
- 修改提案审批时，只检查拟改字段。当前值等于提交时原值，可应用；等于建议值，提示“已实现”；三者均不同，返回该字段的原值、当前值、建议值。未改字段的变化不阻止审批，也不得被覆盖。
- 管理员可以在冲突时明确采用新的当前值为基准、填写最终值并重新提交审批；服务端在同一事务内再次校验该基准。原始建议、冲突时当前值和最终值都要保留。管理员自行提案可自行审批。
- 对 `create_course`，上述六项自动构成共同审批批次；管理员明确勾选的疑似重复提案也可加入同一次审批，即使原教师列表不同。对于修改课程／教师提案，自动组仍须同一目标 ID 与同一拟改字段和值，不跨目标归并。管理员审批其中一份时，整批采用同一个最终结果，即使管理员将原建议改为另一个值；每份提案都保留原建议、各自的最终采用值、作者、匿名设置及通过记录。实体仅创建或修改一次。拒绝是管理员的显式决定，可勾选多份并一次填写共同理由；拒绝确认页必须明确展示本次拒绝的提案 ID 和人数，不因出现已有正式课程而自动改变其他提案状态。
- 审批分为“预览候选／确认结果”两步：预览返回六项相同的自动组、同名疑似待审提案、管理员按课程名模糊搜索到的待审提案、已有课程候选及字段差异；确认提交管理员选择的提案 ID、最终资料和预览版本。手动合并预览须逐份展示原建议、统一的最终资料和预计积分，使管理员能核对教师列表等关键差异。已有正式课程的候选由管理员核对后手动拒绝新增提案。提交时在事务内重新读取并校验候选状态、目标版本和重复判断；候选有变化则要求重新预览，防止审阅与落库之间发生竞态。
- 整批审批与一次实体写入、贡献值结算、资料修改记录、操作日志在 MongoDB 事务中提交或回滚。审批批次有稳定 ID，用于追踪所有成员提案及唯一实体变更。
- 批次审批通过后的 24 小时内可整批撤回；不允许仅撤回某一个成员。撤回一次恢复目标资料、撤回全部成员状态并回扣全部贡献值。目标存在尚未撤回的后续批次更改时禁止恢复，以免覆盖后续更正。课程修改撤回时，只恢复目标课程；该批次创建的教师仅在无其他有效引用时清理，绝不删除其他课程或并非本批次创建的教师。

## 积分、贡献者和公开历史

- 三类提案共用每日提交额度和点赞。管理员与普通用户使用相同贡献值规则。
- 修改提案实际产生变更得基础 1 分；每个最终值与作者建议一致、且确实发生变更的字段再加 1 分，上限 5 分。无实际变更或被拒绝得 0。共同审批批次中的每位不同作者分别按自己的建议计分，同一作者在同批只计一次。新增课程沿用逐字段一致计分，但把原先遗漏的课程代码纳入比较，名称、代码、开课院系、分类、校区、任课教师六项各 1 分，满分 6；历史已结算分数不追溯更改。
- 课程详情将单个 `contributor` 改为 `contributors` 数组，包含未撤回的创建课程和修改该课程提案的公开作者。教师详情包含创建该教师和修改该教师提案的公开作者。按用户去重，按有效审批时间与提案 ID 稳定排序，昵称取当前值。教师资料修改者不自动成为所有相关课程的贡献者。
- 公开历史以一次实际实体变更为一条记录，包含创建事件及后续修改，按批次汇总公开贡献者。修改记录展示原值、作者建议和管理员最终值。每位作者的提案在个人历史中仍单独存在。没有来源提案的旧数据不补造创建事件。
- 匿名提案在公开贡献者、公开历史和其他普通用户可见的提案列表／详情中隐藏作者 ID 与昵称；作者本人及管理员仍可见。操作日志仅管理员可查看真实操作者。撤回的批次不再算有效贡献，也不出现在公开资料历史中。

## 接口方向

以下为目标形状，具体错误码与字段名以实施后的 Swagger 为准：

- 复用 `POST /api/proposal/add`，按 `type` 校验 `course` 或 `targetId + suggested`；旧客户端缺失 `type` 可暂按 `create_course` 解析，但不再依赖 `title`。提交无实际变更建议时返回独立业务错误码。当前统一响应对业务错误使用 HTTP 200、非零 `code`、`data=null`；需要候选详情的响应通过成功的审批预览接口提供，避免要求前端解析错误文案。
- 复用 `POST /api/proposal/:proposalId/approve|reject|revoke`，返回 `decisionBatchId`、受影响提案 ID、目标 ID 和冲突／重复详情。审批请求可携带管理员最终变更与显式冲突重审信息。
- `GET /api/teacher/:teacherId` 返回教师当前资料及贡献者摘要。`GET /api/course/:courseId/history` 与 `GET /api/teacher/:teacherId/history` 分页返回公开资料变更历史。
- 既有提案列表、待审、详情、个人历史、点赞、字段建议，以及课程搜索／详情须按 `type` 返回正确的主体和目标，不能再假设每份提案都有 `course`。
- Swagger 对三种提案输入、字段缺席／清空、冲突三态、精确／疑似重复、候选及差异、批次审批／撤回、匿名权限、贡献者排序、历史分页分别给出可供前端处理的 schema、错误码和示例。
- `GET /api/proposal/field-suggestions?field=courseName` 的课程名建议改为先按名称去重、稳定排序再分页；`total` 为唯一名称数。前端仍选择名称字符串，不需要为此更改交互。

## 操作日志设计

- 管理员原有 `POST /api/changelog/list`、`GET /api/changelog/proposal/grouped`、`GET /api/changelog/proposal/timeline` 继续覆盖三种提案。摘要改为 `type`、目标类型／ID、显示名和变更摘要；不再依赖 `title` 或 `course` 必定存在。
- 每份提案分别保留创建、更新、审批／拒绝／撤回日志，并用 `decisionBatchId` 标出同一管理员决定和自动联动成员；同批实体资料只写一次课程或教师变更事件。管理员全局时间线可展示批次关联，避免把多份通过日志误认作多次资料修改。
- 日志事件保存操作时不可变的结构化快照：原值、作者建议、管理员最终值、目标 ID、批次 ID、触发提案 ID、操作者 ID及是否自动联动。时间线不再用提案当前内容冒充历史快照。管理员日志可展示真实作者，公开历史按匿名规则过滤。
- 分组日志应能查询软删除／重新提交后的历史提案；新分组接口包含软删除提案。补齐撤回动作名称映射，确保不再显示 `UNKNOWN`。日志关键词保持普通文本搜索语义，避免正则元字符造成异常匹配。

## 实施顺序与验证重点

1. 扩展模型与历史读取兼容，建立批次和资料变更记录的稳定关联；保留旧数据可读。
2. 实现课程和教师修改提案、精确／疑似重复与冲突检查、批次审批／拒绝／撤回；修正新增课程现有的“重复却通过”和教师清理所有权问题。
3. 扩展贡献者、教师详情、公开历史与管理员操作日志；修复匿名提案公开身份泄漏。
4. 更新 Swagger 和前端对接说明，按三种类型与共同审批覆盖相关测试、事务并发、积分与撤回回归。

前端适配范围见 [PROPOSAL-EDIT-FRONTEND-MIGRATION.md](./PROPOSAL-EDIT-FRONTEND-MIGRATION.md)。

## 实现与运行

- 所有新提案写入通过同一事务守卫协调，审批预览签名包含候选、最终参数、正式目标版本及同名教师候选。候选增删或资料变化均使旧预览失效；管理员必须重新预览确认。
- `preview.canApprove` 表示资料是否可实际应用；同名新教师候选还需选择已有 ID 或传入 `confirmedNewTeachers`。疑似列表展示待审候选，已有正式课程展示在 `existingCourses` 中。
- 旧课程有来源提案时保留创建历史，但无最终快照则返回 `legacy=true` 并省略 `final`。旧日志缺少快照时也不回填当前提案；历史积分不重算，教师无创建所有权证据时撤回保留。
- 新建的课程撤回后重新审批恢复原课程 ID。积分撤回与重新结算始终按每份提案上次实际发放值处理。同作者手动多选时按提案 ID 顺序仅第一份结算，预览逐份明示。
- 运行需要支持事务的 MongoDB 副本集和 Redis。索引随 ProposalRepo 初始化建立；新增 `proposal_decision`、`feedback`、`feedback_message`、`feedback_read` 集合，无需批量修改旧文档。
- 集成测试使用独立 MongoDB 与 Redis，通过 `MEOWPICK_TEST_MONGO_URI`／`MEOWPICK_TEST_REDIS_ADDR` 配置；每次创建并清理独立测试数据库。
